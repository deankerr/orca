Ordered delivery.
Inspectable history.

discord-delivery turns a collection of webhook calls into durable, ordered work. It remembers what was accepted, what was attempted, what Discord returned, and why something never left the queue.

01

The problem is coordination

Rendering a Discord card produces a payload. Delivering it reliably requires coordination across concurrent producers, HTTP failures, scheduler delays, and investigations hours later.

01

Backfills collide

Independent ingestions can each start sending. Their requests overlap, hit rate limits, and scramble the order that a reader sees.

02

A send has an uncertain edge

Discord can accept a message before the action loses its response. Retrying favors eventual delivery, but can create a second copy.

03

Re-rendering is not evidence

Replaying today's renderer does not tell an agent what an earlier version actually submitted—or which messages were skipped.

02

The contract, precisely

Guarantee within the component

A group keeps the sender

Each group has one destination and an ordered list of messages. Once selected, it holds the global sender through retries until it succeeds, expires, or fails. Other destinations wait too.

Acceptance is transactional: all messages and the task exist together, or none do. HTTP delivery is sequential and can partially succeed.

Deliberate uncertainty

Retry is a policy, not exactly once

Lost outcomes are retried, as requested. The local identity prevents duplicate submissions; it cannot prevent Discord from accepting the same message twice across uncertain attempts.

Retries are bounded. There is no unconditional guarantee that every accepted group will eventually be delivered.

Concept Meaning in this implementation Consequence
sendAt Epoch milliseconds; ordering value, not-before time, identity member, and expiry base. It is not a deadline or a promise of exact send time.
Group identity (destinationKey, sendAt, key) Same identity and content returns the existing group. Conflicting content throws.
Message identity A nonempty key unique inside its group; position follows array order. The same deterministic message key may recur across groups and destinations.
Expiry expiresAt = sendAt + maxAgeMs, when configured. Old work can be accepted, archived, then expire without any HTTP request.
Destination A registered key with a full HTTP(S) URL; the group snapshots that URL. Rotation changes future groups. Accepted groups and later management retain their original route.
Payload A serialized JSON object supplied by the host application. No JSX, builder dependency, or ORCA event knowledge inside the component.
Ordering has a horizon. The worker orders work that has already arrived. If an older historical group arrives after a newer one has started, it cannot go back in time. Strict backfill order requires ordered submission, or pausing the component while the complete set is submitted.

Try the submission identity

Assume destination alerts, sendAt = T, key release:42 already exists.

Reuse the existing group. No new task or HTTP request is created. Re-submitting a failed or expired group does not restart it.

Content equality includes ordered message keys, exact payload strings, retry/expiry policy, reference, and dead-letter destination. Equivalent JSON with a different serialization can conflict. Canonicalization belongs to the caller.

03

A small host-facing interface

The host installs one Convex component and calls its generated function references. There is no separate client class. Authentication, operator access, rendering, and business policy stay in the application. 

// Host convex.config.ts
import { defineApp } from 'convex/server'
import discordDelivery from '@orca/discord-delivery/convex.config.js'

const app = defineApp()
app.use(discordDelivery)
export default app
// Inside a trusted host mutation; components comes from the host's _generated/api.
await ctx.runMutation(components.discordDelivery.api.registerDestination, {
  key: 'dev-alerts',
  name: 'Development alerts',
  url: webhookUrl, // Full URL saved in the destinations table.
})

const groupId = await ctx.runMutation(components.discordDelivery.api.enqueue, {
  destinationKey: 'dev-alerts',
  key: 'release:42',
  sendAt: releaseTimestampMs,
  maxAgeMs: 60 * 60 * 1000, // Optional; no expiry when omitted.
  maxAttempts: 8,          // Optional; budget PER MESSAGE, including its first attempt.
  // deadLetterDestinationKey: 'delivery-reports', // Optional; register this key first.
  reference: JSON.stringify({ releaseId: 42 }), // Opaque to the component.
  messages: [
    { key: 'header', payload: JSON.stringify({ content: 'Release 42' }) },
    { key: 'body',   payload: JSON.stringify(renderedDiscordPayload) },
    { key: 'footer', payload: JSON.stringify({ content: 'End of release' }) },
  ],
})

Mutation surface

  • registerDestination creates/updates a key and clears its disabled state.
  • enqueue accepts an immutable send group.
  • setPaused pauses/resumes the global sender.
  • manageMessage queues a GET, edit, or delete for an original sent message.

Query surface

  • getDestination / listDestinations
  • getGroup / listGroups
  • getMessage / listMessages
  • listAttempts
  • history.groups / messages / attempts / results provide cursor pagination.
Admission bound Current choice Why it matters
Group 1–500 messages; at most 4 MiB of payload bytes. Bounds transaction size and avoids one unbounded submission.
Message JSON object; at most 256 KiB of UTF-8 payload bytes. This is a storage guard, not full Discord schema validation. Multipart file uploads are not implemented.
Retry budget Default 8; configurable 1–100 per message. 429s count against the same budget. Pause preflight skips do not.
Inspection pages 1–500 items requested; default bounded-list limit 100. Payload-heavy pages can still approach Convex read/return limits.

The package is currently a private workspace package. Its reusable boundary exists; publication, a polished external SDK, and a versioned compatibility policy are not finished product features.

04

Keep the evidence. Move the cursor.

The model is a hybrid: immutable accepted work and recorded outcomes, plus a small mutable projection that coordinates delivery. It is not a fully event-sourced system.

Immutable intent

groups

The accepted delivery envelope freezes a destination URL, ordered message count, identity, and policy. Registration changes cannot silently reroute existing work.

destinationId · destinationKey · url · key · sendAt · expiresAt? · maxAttempts · messageCount · reference? · deadLetterDestinationKey?

Writer: enqueueGroup. Indexes support identity checks and time/key/destination investigations. The destination snapshot is intentional duplication.

One owner for progression

The worker mutation advances the cursor, chooses retries, terminates a group, and selects subsequent work. The HTTP action only records an outcome. Two functions do not independently decide what should be sent next.

“Immutable” has a precise boundary

Attempt creation and attaching its scheduler ID happen in the same transaction. Results are appended once. Tasks and global control remain mutable; there is no replay engine that reconstructs them from an event stream.

Separating payloads from hot state keeps retries from rewriting large bodies. The price is seven tables, several indexes, and joins for inspection. This is more machinery than a two-table outbox, chosen to make uncertain attempts and management history first-class records.
05

One delivery, end to end

  1. Accept. Validate bounded JSON work. Read the identity index. Store immutable rows plus one task, and ping the named delivery worker in the same mutation.
  2. Select. If no group is active, choose the earliest queued sendAt. A future group waits until eligible. Once active, its cursor determines the only message that can run.
  3. Claim. Re-read all eligibility in the mutation because Batch Worker's query snapshot can be stale. Create an attempt, schedule its action, and save the active attempt ID transactionally.
  4. Perform. The action rechecks its fence, pause, and expiry. The transport performs one request with a 20-second timeout covering response-body reading.
  5. Record. Insert one result if that attempt is still current. Duplicate result writes are ignored; stale attempts cannot overwrite a newer attempt.
  6. Progress. Consume the result before another request can be claimed. A successful final message completes the group and releases the sender.
Scheduler overlap is not HTTP overlap. A completed HTTP request can have its result consumed while its action finishes bookkeeping. The invariant is one active local request, not that two action invocations can never briefly coexist. After a timeout, Discord might still finish processing an uncertain request; local serialization cannot guarantee remote completion order in that case.

07

Failure is part of the protocol

Observation Worker decision What remains true
HTTP 2xx Advance the cursor, reset that message's attempt counter. Original payload and response remain separate records.
2xx headers, body lost Keep the known success; record the body-read error. No blind duplicate retry. Without a receipt ID, management is unavailable.
429 or exhausted bucket Honor the largest recognized delay; hold the global sender. 429 retries also use exponential backoff. A different destination cannot jump ahead, even if its own bucket is free.
Network uncertainty / 5xx Retry the same message, within its budget. A lost response can mean Discord already has a copy.
Permanent error / budget exhausted Fail the group; stop its remaining messages. Already confirmed messages stay sent. There is no rollback of Discord side effects.
Send returns 401 / 403 / 404 Also disable the registered destination if its current URL matches the group's snapshot. Re-registration clears disabled state. Management errors do not disable a webhook.
Expiry before request Expire the group without another HTTP request. A success received after expiry still counts; remaining messages can expire.
Pause before preflight Record a skipped attempt; restore its retry budget. Pause is not cancellation. A request that already passed preflight may complete.
DELETE 404, Discord code 10008 Treat “unknown message” as already deleted and complete the operation. Keep the actual 404 response as evidence; other 404s still fail.

Backoff has two clocks

Retry delay is the maximum of the received rate delay and exponential backoff: 1s × 2^(attempt−1), capped at 60 seconds. There is no jitter.

Rate limits can extend past that cap. Long valid deadlines are honored through scheduler sleeps of at most 24 hours each. Eight attempts does not bound total wall-clock time.

Dead letter means a summary

Failed and expired groups always produce a warning log. An optional registered destination receives a new one-message group containing a bounded terminal summary and original group ID.

The complete payloads stay in the archive. This summary uses the same sender, can itself fail, and does not recursively forward its own failures.

Recovery asks the scheduler, not just a timer

The worker also recovers a scheduler invocation marked successful if no result was persisted. That is explicitly uncertain, not evidence that the webhook failed. If an execution remains inProgress indefinitely, the sender waits; the design depends on Convex execution-state accuracy and Batch Worker liveness.

const page = await ctx.runQuery(components.discordDelivery.history.results, {
  from: morningStartMs,
  to: morningEndMs,
  paginationOpts: { numItems: 50, cursor: null },
})
// Each result links to the exact local message and group.
// Fetch message.payload, inspect response.body, follow attempts for retries.
// Continue with page.continueCursor until page.isDone, including empty filtered pages.
const message = await ctx.runQuery(components.discordDelivery.api.getMessage, {
  messageId: localMessageId,
})

Evidence hierarchy

  1. Accepted message: exact serialized payload.
  2. Attempt: a scheduled request, which may have been skipped before HTTP.
  3. Result: status, headers, body, receipt IDs, errors, or explicit uncertainty.
  4. Task: why the group ended and which positions completed.

A result may appear briefly before the worker advances the derived message status. Inspect both when investigating active work.

Finding what was not sent

Query groups by intended time, destination, key, or terminal status, then inspect their messages and attempts. “Failed” on a remaining message can mean it was never attempted because an earlier message failed.

Do not infer HTTP contact from an attempt row alone. A preflight skip has an attempt and a result, but made no network request.

Bounded lists are convenience views. listGroups examines at most 500 indexed candidate groups, then applies task-status filtering and the requested result limit. It is not an exhaustive status search. Paginated history can return an empty filtered page with isDone = false; continue reading.

Get, edit, and delete keep their own history

const editGroupId = await ctx.runMutation(
  components.discordDelivery.api.manageMessage,
  {
    messageId: originalLocalMessageId, // Local messages ID, not Discord's snowflake.
    operation: 'edit',                 // Or 'get' / 'delete'; those omit payload.
    key: 'correction:42:v1',
    sendAt: Date.now(),
    payload: JSON.stringify({ content: 'Corrected release details' }),
  },
)

This creates a new group linked by sourceMessageId. It uses a confirmed remote message ID and the original URL snapshot; it does not overwrite the original send or pretend the old payload was always correct. A forum/media thread created by a send is routed using the receipt's channel ID when needed.

The archive is not a continuously synchronized view of Discord: external edits or deletes require another GET to observe them. Management joins the same global queue. It has no priority lane and currently exposes neither a retry-budget option nor expiry. It requires a confirmed receipt: uncertain extra copies cannot be located or managed from this ledger alone. Arbitrary URL destinations still need to implement Discord-compatible routes and responses for management to work.

09

Inside the package

The important seam is between deciding what should happen next and performing one external side effect. The remaining modules support admission and investigation without importing host-domain concepts.

Host boundary
api.ts

Destination registration, enqueue, pause, management, and bounded inspection. Translates public component operations into internal queue behavior.

Admission
queue.ts

Validates work, checks identity, writes group/message/task rows, accesses shared control, and pings Batch Worker. Both normal sends and management use this admission path.

Progression owner
worker.ts

Work query, eligibility recheck, attempt claim, result recording/consumption, retries, scheduler recovery, terminal transitions, and dead-letter summaries.

External side effect
request.ts

Preflight reads the active-attempt fence, pause, and expiry; the action executes one request and commits its result. No self-retry or cursor advancement.

Protocol
transport.ts

HTTP method/URL construction, timeout, raw response capture, receipt parsing, and rate-delay interpretation. Injectable fetch keeps protocol tests independent of Discord.

Read model
inspection.ts + history.ts

Shared indexed selection and derived message/attempt views; cursor pagination through convex-helpers. Bounded and paginated APIs share filter semantics.

Stored and returned shapes
schema.ts + validators.ts

Tables, indexes, operation/status unions, query arguments, and validated return views across the component boundary.

Loop liveness
convex.config.ts + Batch Worker

Installs Batch Worker. The named loop asks for work or an idle timeout; the delivery package owns ordering, grouping, retry policy, and all delivery evidence.

The reusable unit is delivery intent

The component knows destinations, groups, messages, operations, and receipts. It does not know scans, ingestions, endpoint changes, filters, pricing thresholds, or Discord.js builders. reference is an opaque caller string, not a hidden ORCA schema.

The transport sets wait=true for sends to obtain receipts and with_components=true when a payload includes components. It preserves destination query parameters, uses message routes for management, and rejects HTTP redirects. Full URLs are accepted; a generic transport adapter system is not implemented.

The choices behind the machinery

Some choices follow the brief directly. Others narrow an ambiguous requirement or add implementation policy. These distinctions matter when deciding what to keep.

Decision Relationship to the brief Tradeoff / alternative
One global component and active group Aligned
Honors no interleaving, including across destinations. 		Maximum simplicity of ordering; accepts head-of-line blocking. Per-destination lanes would improve throughput but need global rate coordination and a revised ordering contract.
Batch Worker drives the loop Recommended option selected
Uses the one-process/table-drain model suggested in the brief. 		Workpool's completion/control separation and scheduler recovery informed the design. A concurrency limit of one alone does not keep a group's retries ahead of other jobs.
Seven tables; hybrid state Implementation choice
Expands the suggested group/task and message records into explicit evidence and control. 		More joins and schema surface. A simple mutable outbox is smaller; full event sourcing offers replay but adds projection/reconstruction complexity.
Retry uncertain outcomes Explicit user decision
Possible duplicates are accepted. 		Skipping uncertainty reduces duplicates but risks missing accepted work. Local dedupe cannot supply remote exactly-once semantics.
Eight attempts by default; 429 counts Implementation choice
The brief did not specify this policy. 		Finite failure behavior; persistent throttling can exhaust a message's budget. Separate throttling/retry budgets could be considered if this occurs.
Every rate delay is global Conservative choice
Stronger blocking than per-webhook Discord buckets require. 		Avoids concurrent floods and fits strict group affinity. It leaves throughput unused and can postpone unrelated destinations.
Dead-letter summary through the same queue Narrowed
Implements the optional failure destination as a bounded report, not a full original-payload forwarder. 		Easy to inspect and no recursive failures. It is not an independent, guaranteed emergency channel or a pluggable logging sink.
Arbitrary HTTP(S) URLs, Discord protocol Scope boundary
Supports custom receivers without forcing discord.com. 		URL flexibility does not make this a general “anything anywhere” transport. JSON-only payloads and Discord route/receipt assumptions remain.
No JSX extraction; no production composer Aligned with revised brief
Discord.js builders remain host-side; custom payload iteration is a dev workflow. 		The primitive can serve future broadcasts/status alerts. Those product workflows are not implemented by the component.
Full retention Deferred as requested
No TTL, pruning, or payload zeroing. 		Maximum evidence now; future cleanup must preserve references, dedupe meaning, and management requirements.
Why not Workpool with maxParallelism = 1?

That bounds concurrency, but the requirement is also group affinity: once A starts, its delayed retries must retain the sender ahead of B. Modeling each message as an independent job would need additional coordination. Modeling each group as one job is viable, but still needs a global coordinator for deadlines, cooldowns, and durable message evidence. Batch Worker avoids a second delivery-job model here. Workpool becomes more attractive if independent destination concurrency becomes a goal.

Why not a durable Workflow per group?

A workflow can express a sequence of messages and retries, and would suit richer multi-step business processes or compensation. It would still need coordination across workflows to enforce the current global non-interleaving rule. This component's problem is primarily draining one owned queue, so a central state machine is the smaller fit.

Why not the old action + short sleep?

It remains reasonable for an isolated disposable demo. It does not solve collisions between separate invocations, durable investigation, coordinated expiry, or resuming an interrupted group. Using the real queue for dev iteration also exercises the path whose output is being investigated.

ORCA is a caller, not the component

Application-owned

ORCA alerts

Ingest events → preparation obligation → filtering → batching/order → Discord.js builders → serialized payloads.

Owns route selection, automatic-send policy, historical scan references, and operator workflows.

→
Reusable component

Delivery groups

Accept → schedule → send/retry/expire → preserve evidence → inspect or queue management.

Receives only keys, times, destinations, opaque references, and JSON bodies.

Automatic alerts

ORCA records preparation work with event ingestion and captures routes. Preparation renders the applicable events and enqueues route groups; its completed state prevents repeated automatic preparation.

Historical scan_at maps to sendAt. Route expiry can naturally archive old alerts as expired. The component does not need to understand why the timestamp is old.

Repeated dev demonstrations

demoScan(scan_at, destinationKeys) reads the same historical scan and uses current filtering, batching, and card construction. Each invocation gets fresh identity and sends now, without expiry.

It bypasses the automatic preparation record, retains earlier runs and Discord messages, and does not delete production alert state to defeat dedupe.

The two times are deliberately separated in dev. The historical scan remains the rendering context/reference. The group's current sendAt makes another iteration eligible immediately. Repeated demos test current output, not what the historical automatic run actually emitted.

The current demo helper requires explicit destination keys, rejects missing/oversized scan selections, and can return no groups when everything is filtered. It is an internal operator function intended for dev; it does not have a hard deployment-tier guard. That intent is a workflow convention, not an enforced production prohibition.

Future status messages, manual broadcasts, milestones, filtered routes, and experimental renderings can use the same component. Their trigger, formatting, and authorization belong in ORCA. See ORCA alert operations, alerts expansion requirements, and configuration for application-specific details.

12

What to watch, and what is proven

Durability makes failures inspectable; it does not remove them. These are the concrete limits of the current implementation and the conditions that would justify another design pass.

Weakness / limit Practical effect What would improve it
Global head-of-line blocking A slow destination, large group, or long rate deadline delays everything—including management and dead-letter summaries. Keep current policy while strict order matters. Revisit destination lanes or explicit priority only with a changed contract.
Unbounded response-body capture Request payloads are bounded, response bodies are not. A custom receiver can return a body too large for a Convex result record; persisting the outcome can fail and turn into uncertain retries. Define a byte cap and truncation marker, or move large bodies to storage. This remains an implementation gap.
Evidence does not enumerate uncertain copies A remote message accepted without a saved receipt may exist, but its ID is unknown. The ledger cannot prove absence or find every duplicate. A reconciliation strategy would require additional remote capabilities. Do not present this as exactly-once delivery.
Bounded queries, potentially large documents 500 rows can contain far more data than a practical query response allows. Status filtering is post-pagination; payload search is client-side. Use small pages now. Add metadata-only views, byte-aware limits, or dedicated search if the archive grows.
Scheduler and worker dependency The sender relies on correct scheduler state and Batch Worker wake/recovery behavior. Persistent pending/in-progress execution can hold the queue. Add operational health/age signals and realistic fault testing before stronger availability claims.
No cancellation or terminal-group restart API Re-enqueueing the same identity returns its terminal group. There is no selective cancel, reorder, or “retry failed group” command. Use deliberate new identities when appropriate; add operations only with clear historical and ordering semantics.
Pause and expiry are preflight checks They cannot atomically retract a request after it passed the check. Partially delivered groups stay partially delivered. Document this boundary; remote rollback is a separate feature, not something a database transaction can supply.
URL snapshots and retained credentials Rotated URLs remain in historical groups and may still be used. Raw URLs/bodies require trusted operator access. Arbitrary outbound URLs should not be user-controlled through an unauthenticated wrapper. The host must control registration and inspection. Future redaction/retention would need an explicit compatibility policy.
Dead-letter path shares failure modes A report waits in the same queue and can fail. The sink key resolves when the report is created, not when the original group was accepted. An independent reporting integration is a future alternative. Avoid ad hoc table deletion that breaks referenced destinations.
No retention strategy yet Every payload, attempt and response accumulates; retries amplify archive size. Measure actual volume first. Payload zeroing or storage offload must preserve useful audit evidence and dedupe behavior.
