## OpenRouter

- OpenRouter's API endpoints are cached by Cloudflare, have extremely heavy and wasteful data structures, and are pinged constantly while you're on their website. They do not notice or care how often you're hitting them.

- We can only know if an endpoint is no longer available by querying for endpoints of that model, successfully retrieving a result and comparing it with our current knowledge of existing endpoints. If we fail to fetch a result, we have to explicitly declare it as such, otherwise it can look like those endpoints are gone when performing a simple diff of the total collected endpoints dataset vs existing. This is issue is further complicated by the fact that if a model has 0 endpoints, the endpoints endpoint returns a 404 error.

## OR's Data Model

- (/frontend/models) slugs with a `~` prefix, e.g. `~openai/gpt-latest, ~anthropic/claude-fable-latest` are pointers and their permaslug does not yield endpoints.
  - this list tells every model OR has on record. if the model has an embedded `endpoint` (a single "top" endpoint), that means it has data for us to query from the `endpoints` endpoint - this is the data we actually care about.
  - if `endpoint` is null, it has no endpoints, meaning it is unavailable for inference.
  - it contains records for models that are long since deprecated (e.g. openai/gpt-3.5-turbo-0125, anthropic/claude-instant-1), which is not useful for us since our focus is on endpoints.

- I think its worthless to store provider data policy, because endpoints can override it. therefore it is not "always" true. so we could never claim "this provider doesn't retain prompts". the endpoint-centric view would be "this provider doesn't retain prompts on any of their endpoints."
  - the url fields (e.g. `terms_of_service_url`) are an exception - these are standard per provider and should live there.

### The Truth About Providers

(Dean)

```
this is somewhat bewildering, and something i didn't model quite right in my backend schema.

azure/eu and azure are the same provider, Azure. azure/eu is more like a provider "variant", with its own display name. it exists to distinguish endpoints from the provider, and allows users to target it specifically (usually). but it only exists in the context of an endpoint, and has no properties of its own.

but then what is the FK? provider_name, Azure. yes, it's true.
```

(Claude)

```
provider_name is the only join that never breaks. Every endpoint's provider_name matches exactly one group of provider_info records, with no orphans. Fifteen orgs have multiple provider records (Azure: azure, azure/eu; Google: six google-vertex/* slugs; Amazon Bedrock: five; …).

Slug prefixing is genuinely unreliable, not just awkward. Two counterexamples kill it: sambanova-turbo is a variant of SambaNova with no slash at all, and — my favorite — anthropic/claude-on-aws is a provider record whose name is "Amazon Bedrock". A slug living under anthropic/ belonging to a different org. So there is no structural rule that recovers the org from the slug; the display string really is the FK.

The variant records carry almost nothing of their own — same-name records differ only in slug, displayName, and routing wiring (baseUrl, adapterName, pricingStrategy). Your "no properties of its own" is right conceptually; what they do have is how OR reaches them, not provider facts.

And there's a third naming layer below that. Endpoint provider_slug values like azure/swedencentral or novita/fp8 have no provider_info at all — the qualifier is a region or quantization, with provider_region/quantization sometimes echoed as fields. Worse, the same qualified slug appears with different provider_display_names on different endpoints (amazon-bedrock/eu-west-1 shows up as both "Amazon Bedrock" and "Amazon Bedrock (EU)") — so display name isn't even a function of provider_slug; it's a per-endpoint property.
```
